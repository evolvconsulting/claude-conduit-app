THE UNINSTALL TIMEOUT (the handover's open issue) — NOT a hang in uninstall.js/pm2Control. Diagnosed by reproducing directly, in layers:
- Engine layer exonerated first: node -e driving uninstall() against a real running proxy, with per-sub-step timing, completed in 629ms total (pm2 delete 624ms, pm2 dump 2ms), including with a pm2 log-tail bus open and the status poller ticking. Purge and keep modes both fine.
- Root cause was in the RENDERER, and was two separate defects (below), one of which only reproduces intermittently.

BUG 6 — window.confirm() freezes the entire renderer (uninstall-view.js, claude-desktop-view.js). Electron's window.confirm is a *blocking* native modal: while it is up, no timers, no IPC replies, no repaints. Proven live: with the dialog open the renderer stopped answering CDP evaluations entirely for its whole lifetime; with it stubbed, the same click completed in 805ms. This is exactly what the previous session's 15s driver timeout was. The plan called for a confirm-dialog component that was never built. Fixed: new src/renderer/components/confirm-dialog.js — promise-based, uses the native <dialog> element (real focus trap, Esc-to-cancel, backdrop) and stays asynchronous. Both views migrated. Regression-guarded by a test that fails if confirm/alert/prompt reappear anywhere in src/renderer (verified the guard actually fires by reintroducing the call).

BUG 7 — the uninstall summary was destroyed before it was ever painted. runUninstall() set '#uninstall-result' then immediately called navigate('setup'), and the router clears the container on every route change. Frame-by-frame DOM trace (10ms resolution) showed the transition go straight from empty -> '<<element gone>>' + Setup: the user never learned what was removed, and in keep mode never saw where their config still lives. Fixed: the summary now replaces the view (removed list, kept paths, Claude Desktop status) and waits for an explicit 'Back to Setup' acknowledgement.

BUG 8 — INTERMITTENT STALL, the reason the failure looked non-deterministic. After fixing 6 and 7 the uninstall still hung in roughly 1 run in 3, always at a confirm dialog, with no renderer exception, and a main-process watchdog polling the DevTools HTTP endpoint recorded ZERO main-process stalls. Isolated with a stress harness: the apply-via-dialog flow ran clean for ~19-23 rounds then stalled for ~5 rounds (dialogs accumulating in the DOM, closed but never removed, returnValue correct) and then RECOVERED on its own. Root cause: Chromium throttles/suspends a renderer whose window is occluded or backgrounded, which suspends <dialog> 'close' event dispatch (a top-layer/rendering update) — so the confirm promise never settles and the confirmed action silently never runs until the window is brought forward. Confirmed by running with --disable-backgrounding-occluded-windows (40/40 clean vs. stalls without). Fixed IN THE APP, not the harness: backgroundThrottling:false in windows.js. This is a genuine user-facing fix, not a test workaround — a proxy manager is expected to sit behind other windows, and the same throttling stalls the live log viewer and the status pill. After the fix: 40/40 stress rounds clean with no CLI flags, and two consecutive clean e2e runs.

BUG 9 — the Dashboard log viewer was permanently blank on a healthy idle proxy. pm2's log bus only streams output produced AFTER it attaches, so opening the Dashboard on an already-running proxy showed nothing at all despite ~2.2KB of real startup log on disk — it looked broken. Proven by measuring: viewer empty after 5s idle, then a single real request through the proxy produced a line in ~4ms (so the tail itself was fine). Fixed: new proxy:get-recent-logs IPC reusing the existing pm2Control.tailLastLines (which was implemented but never exported), and the Dashboard now seeds the viewer with the last 200 lines of out/err before streaming.

BUG 10 — the tray could crash app startup, violating AC#4. new Tray() throws outright on Linux with no AppIndicator/StatusNotifier host, and createTray() was unguarded and called unguarded from index.js. Fixed: createTray now returns a null-object tray (available:false, no-op setStatus) on any failure, and setStatus is individually guarded so a tray that breaks mid-session cannot take the status poller down. Dependencies are injectable so this is unit-testable outside Electron; 6 new tray tests cover both fallback paths, live status reflection, start/stop/restart enablement, and that Quit calls only quit().

ALSO ADDED (task description gap): the Uninstall view was missing the 'separately-confirmed Claude Desktop revert checkbox' the description calls for — it only told the user to go elsewhere. Now an opt-in checkbox that triggers its OWN second confirmation dialog, so a Claude Desktop revert can never ride along on a click meant only for the proxy. The engine (uninstall.js) still never touches Claude Desktop; the view calls claudeDesktop.revertToDefault() separately and reports its outcome in the summary.

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found during NCOW-25's wave-9 review (2026-08-02/03) while verifying the packaged Linux
cold-bootstrap path for the first time. Independently reproduced live by the reviewer on TWO
real packaged artifacts (packaged macOS via `npm run pack`, and the packaged Linux arm64
AppImage) -- byte-for-byte the same failure on both.

Root cause (re-derived from source): configGen.js's renderEcosystemConfigCjs() deliberately
omits an `interpreter` for the managed litellm-nim app entry (comment: "pm2 auto-detects the
.js extension"). pm2's Common.js resolveInterpreter maps `.js` to the literal string `"node"`.
God/ForkMode.js's forkMode() then builds the child's argv by resolving
`path.resolve(path.dirname(module.filename), '..', 'ProcessContainerFork.js')` -- inside a
packaged build, `module.filename` is an app.asar-internal path
(`.../app.asar/node_modules/pm2/lib/God/ForkMode.js`), so this argument is handed to a
PATH-resolved SYSTEM Node.js binary that has no asar support: MODULE_NOT_FOUND, crash loop,
HEALTH_CHECK_TIMEOUT.

This is the exact class of problem NCOW-22 already solved for the pm2 DAEMON itself (via
process.execPath + ELECTRON_RUN_AS_NODE=1 in pm2Control.js's spawnDaemon()) -- but nothing
equivalent exists for the MANAGED APP pm2 launches on the daemon's behalf.

Confirmed NOT architecture- or platform-specific: gated purely on `asar: true`. It breaks
every published artifact on every platform/arch this project ships (macOS, Windows, Linux;
x64 and arm64) -- source/dev runs are immune because pm2 then resolves a real filesystem path
instead. Confirmed why no prior wave caught this: NCOW-22's start/stop/restart verifications
on all 3 platforms were all SOURCE runs; its only packaged-artifact test exercised daemon
bootstrap + getStatus() (which never forks the managed app). NCOW-10.3's real end-to-end
auto-update verification on Windows relied on a manually pre-started, already-running pm2
daemon with litellm ALREADY running under it (per its own recorded scope caveats) -- so it
never exercised a genuinely fresh proxy.start() from a packaged install either. No wave has
ever actually called proxy.start() from a packaged artifact, on any platform, until now.
Practical implication: every currently published release (v0.1.0, v0.1.1) has never been
proven to actually start litellm via a real packaged install.

A fix recipe was independently validated live by the reviewer: adding to the generated
ecosystem entry in configGen.js's renderEcosystemConfigCjs() --

    interpreter: process.execPath,
    env: { ELECTRON_RUN_AS_NODE: '1' },

-- fixed packaged macOS start/stop/restart end-to-end, including a real HTTP 200 completion
through the running proxy. Two non-obvious points the reviewer flagged for whoever implements
this: (1) `process.execPath` must be written as a literal expression in the generated .cjs,
not a value interpolated/frozen at generate time, since the file is require()'d by whichever
binary is currently running the pm2 client; (2) the explicit `env` entry is load-bearing --
God.forkMode builds the child's env from pm2_env alone, so a pre-existing daemon this app
didn't spawn (a user's own global pm2) has no ELECTRON_RUN_AS_NODE, and without it the
interpreter would boot a second GUI copy of the app -- the exact hazard NCOW-22 already
documented for the daemon itself.

Two open questions the reviewer flagged as needing investigation, not yet answered:
- Windows is entirely untested for this specific failure (only macOS and Linux were
  reproduced/fix-verified).
- A real unresolved design question specific to AppImage packaging: `process.execPath` inside
  a running AppImage is an ephemeral per-launch FUSE-mounted temp path
  (`/tmp/.mount_XXXXXX/claude-conduit`), and pm2 persists the interpreter path into
  `dump.pm2`, so `pm2 save`/`resurrect`/autorestart-after-quit would reference a dead path
  once the AppImage unmounts. This entangles with NCOW-24's already-filed daemon-persistence
  concerns and should be considered alongside it.

This also means the "Done" evidence recorded on NCOW-10 (parent epic) and NCOW-22 should be
read with this caveat: their live proxy-restart/cold-bootstrap verification was real and
correctly scoped to what each set out to prove, but none of it was ever exercised from a
genuinely packaged artifact calling proxy.start() cold -- that specific gap is what this task
closes.

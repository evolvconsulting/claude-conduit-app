## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Implement switching the active connection: regenerate litellm.env/config.yaml from the newly-active connection and restart the proxy, with visible progress and a clear result. Per the approved decisions (2026-08-28): Claude Code's settings.json and Claude Desktop's config entry (port, master key) stay fixed across every switch - only the upstream credential/model routing changes - so clients never need reconfiguring; an in-flight request on the connection being deactivated is allowed to finish before the proxy restarts.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Exactly one connection is active at a time and which one is unambiguous throughout the UI
- [x] #2 Switching regenerates the LiteLLM config from the newly-active connection and restarts the proxy, with visible progress and a clear success or failure result
- [x] #3 Claude Code's settings.json and Claude Desktop's config entry (port, master key) are unchanged by a switch - documented as the approved decision, with reasoning
- [x] #4 An in-flight request against the connection being deactivated is allowed to finish before the proxy restarts - documented as the approved decision, with reasoning
- [x] #5 A documented decision records the single-proxy-vs-multi-proxy reasoning, derived from this task's own AC#1/#2 (exactly one active connection, restarts 'the' proxy)
- [x] #6 Every connection credential stays in OS-backed secret storage through a switch, never written into the config directory
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Lock shape decision (read ipc.js/mutex.js in full first): `connections.activate` needs `config` + `proxy` locks — NOT claudeCode/claudeDesktop, and NOT the full 4-lock `settings.updatePort` shape. Reasoning: activate regenerates litellm.env/config.yaml (config domain) and restarts the pm2-supervised proxy (proxy domain), but per AC#3 it must NEVER touch Claude Desktop's config entry or Claude Code's settings.json (port/master key stay fixed, so there is nothing in those files to reapply) — updatePort needs claudeCode+claudeDesktop only because IT changes the port those files embed; activate does not change the port. Since DOMAIN_MUTEX_ALIASES resolves locks per-DOMAIN (all of connections' methods share one lock set today, aliased to 'config' alone), and activate's sibling CRUD methods (create/update/duplicate/delete) must keep their existing single-`config`-lock scope (widening the whole domain would make unrelated CRUD edits queue behind proxy restarts and vice versa — needless contention, against this file's own NCOW-50 minimal-locking precedent), I'm adding a new per-METHOD override mechanism to ipc.js: `METHOD_MUTEX_ALIASES = { connections: { activate: ['config', 'proxy'] } }`, resolved by a new `resolveMethodLocks(mutexes, domain, method)` (extracting the domain-name-list -> locks logic out of `resolveDomainLocks` into a shared `resolveLocksForDomainNames` helper), consulted per-method in `registerIpcHandlers`'s loop instead of once per domain. Add matching module-load validation (domain.method exists in CHANNELS, target domains exist in LOCK_ACQUISITION_ORDER, no empty override) mirroring assertLockOrderIsConsistent/assertAliasKeysAreKnownChannelDomains, and deep-freeze the new table. `activate` stays OUT of UNSERIALIZED_METHODS.connections (it must be locked, unlike list/listProviders/validateCredential/listModels).
2. ipc-channels.js: add `activate: 'connections:activate'` to the `connections` domain's invoke map (preload auto-derives `nimProxy.connections.activate` from this, no other preload change needed).
3. engine-context.js: add `connections.activate({id})` handler, alongside the existing `connections.*` CRUD handlers:
   - getManifest(); NOT_CONFIGURED if null.
   - connectionsEngine.findConnection(manifest, id); NOT_FOUND if missing.
   - No-op short-circuit if `id === manifest.activeConnectionId` (mirrors updatePort's identical-port no-op) — return {ok:true, data:{manifest, changed:false}}, no regen/restart.
   - resolveProviderOrError(connection.provider).
   - secretStore.loadFor(id); if the provider's declareCapabilities().requiresApiKey and no key on file, NO_KEY.
   - Known-bug-class guard: force a FRESH provider.validateCredential({apiKey, baseUrl: connection.nim_base_url}) call before switching anything live — a connection's credential may have been revoked/expired since it was last saved, and CCA-15.3 is explicitly the point where "which credential drives the live proxy" changes, so this must not blindly trust a possibly-stale prior validation. Return the validation failure verbatim (no manifest/file writes yet) on failure.
   - Guard: connection.primary_model/small_model both set (defensive; real UI connections always have both, but configGen would otherwise bake literal "undefined" into config.yaml).
   - prereqs.checkLitellmOnPath(); LITELLM_MISSING if absent.
   - port = manifest.port ?? DEFAULT_PORT (handles the "connection created but config.generate/Setup's proxy step never ran" case — CCA-15.2's create() can make a connection "active" in manifest data without ever calling config.generate).
   - configGen.generateAll({... connection's own provider/model/baseUrl, port, resolved apiKey ...}) — same call shape as config.generate/updatePort.
   - saveManifest({activeConnectionId: id, port, primary_model, small_model, nim_base_url, provider, litellm_path, pm2_app: pm2Control.APP_NAME, cli_configured: existing?.cli_configured ?? false, secret_store_backend: 'electron-safeStorage', generated_by_version: deps.appVersion}) — persisted BEFORE the restart attempt, mirroring updatePort's established "write then attempt restart, report failure but keep the write" precedent (settings-view.js's updatePort caller already tolerates this shape: on !ok it just toasts, doesn't roll back local state).
   - pm2Control.startOrRestart(...); broadcast proxy:status-changed; on !restart.ok return {ok:false, error:restart.error, data:{manifest:updated, outTail, errTail}} (known-bug-class: never treat this as success).
   - Deliberately NO Claude Desktop/Code reapply tail (unlike updatePort) — AC#3 says those stay unchanged, so this handler must never touch claudeDesktopConfig/claudeCodeConfig at all, which is also *why* it needs no claudeCode/claudeDesktop lock.
4. AC#4 evidence (verified by reading pm2's own source under node_modules/pm2, not assumed): pm2Control.startOrRestart() calls deleteAppIfPresent() -> pm2.delete -> God.deleteProcessId -> God.stopProcessId -> God.killProcess, which sends SIGINT (cst.KILL_SIGNAL, PM2_KILL_SIGNAL-overridable) to the process tree and polls up to pm2_env.kill_timeout (our ecosystem.config.cjs sets 10000ms) before escalating to SIGKILL (God/Methods.js processIsDead). Our generated run.js launcher forwards SIGTERM/SIGINT/SIGHUP to the actual litellm child (stopChild()), and litellm (uvicorn/FastAPI) does a standard graceful shutdown on SIGINT/SIGTERM — stop accepting new connections, let in-flight ones finish — before exiting. Only after that stop settles does startOrRestart() call pm2.start() for the newly-active connection. So AC#4 is satisfied BY CONSTRUCTION, with no new drain logic needed in connections.activate — it just has to not do anything that pre-empts this (e.g. no manual kill before calling startOrRestart, which it doesn't). Windows caveat carried over from CLAUDE.md/configGen.js's own documented note: no real POSIX signals there, so this graceful behavior is a macOS/Linux guarantee; Windows degrades to a harder stop, an existing, already-documented platform limitation this task does not change.
5. AC#3/#5 are documented decisions already approved on CCA-15's own plan — restate with reasoning as this task's own notes/summary (not re-decided), and evidence is: activate's handler literally never calls claudeDesktopConfig.*/claudeCodeConfig.* (verifiable by reading the handler), and the single-proxy reasoning follows directly from this task's own AC#1 ("exactly one connection active") + AC#2 ("restarts the proxy", singular) as CCA-15's plan already lays out.
6. No change to where secrets rest between switches; verify by grep confirming connections.activate touches only secretStore.loadFor (never .save/.saveFor) and configGen's existing writeSecretsEnvFile path.
7. Renderer — setup-view.js: track `state.activeConnectionId` (from connections.list()'s activeConnectionId) and `state.activating` (connection id or null). Connection cards: render an "Active" badge on the currently-active card, an "Activate" button on every other card (disabled while any activation is in flight, showing "Activating…" on the specific card being activated). handleActivate(id) calls nimProxy.connections.activate({id}); on failure, toast the error message (visible failure result) and stop; on success, toast success, syncManifestState(result.data.manifest), update state.activeConnectionId, re-render (no full loadLibrary() refetch needed — the connections list/count is unchanged by activation).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
IMPLEMENTATION SUMMARY

Added `connections.activate({id})` (engine-context.js): regenerates litellm.env/config.yaml from the newly-active connection (configGen.generateAll, same call shape as updatePort/config.generate) and restarts the proxy (pm2Control.startOrRestart). Forces a FRESH provider.validateCredential() call before switching anything live (known-bug-class guard from the campaign brief — a connection's credential may have gone stale since it was last saved, and this is the point where "what's live" actually changes). Deliberately never calls claudeDesktopConfig.*/claudeCodeConfig.* — AC#3's port/master-key-stay-fixed decision means there's nothing in those files to reapply. Persists the manifest patch BEFORE attempting the restart (mirrors updatePort's own precedent, tolerated identically by its callers).

LOCK SHAPE DECISION (AC-independent but load-bearing): `connections.activate` needs `config`+`proxy`, not the 4-lock `settings.updatePort` shape (it never touches claudeCode/claudeDesktop state) and not its `connections` CRUD siblings' single-`config`-lock shape either (they never touch proxy state). ipc.js's DOMAIN_MUTEX_ALIASES only resolves locks per-DOMAIN, so widening the whole `connections` domain would force unrelated CRUD edits to queue behind proxy restarts and vice versa — needless contention, against this codebase's own NCOW-50 minimal-locking precedent. Added a new, parallel per-METHOD override mechanism (`METHOD_MUTEX_ALIASES`, `resolveMethodLocks()`, extracted `resolveLocksForDomainNames()` shared with `resolveDomainLocks()`, plus matching module-load validation/deep-freeze — same discipline as the existing DOMAIN_MUTEX_ALIASES machinery). `connections.activate: ['config', 'proxy']` is the one entry today; every other connections method still resolves through the unmodified domain-level path (proven directly in ipc-mutex.test.js).

AC#3 (Claude Code/Desktop config unchanged by a switch) — approved decision restated with reasoning: activate() never calls claudeDesktopConfig.*/claudeCodeConfig.* at all, because port and the litellm master key (the only two things those files encode) are system-level, not per-connection (CCA-15.1), and stay fixed across every switch. Verified live: a real settings.json (via claudeCode.configure()) is byte-for-byte identical before and after a real connections.activate() call (engine-context-connections.test.js's new AC#3 test) — not just "the code doesn't call it," a real file comparison.

AC#4 (in-flight request finishes before restart) — approved decision restated with reasoning, verified by reading pm2's own source (node_modules/pm2), not assumed: pm2Control.startOrRestart()'s deleteAppIfPresent() -> pm2.delete -> God.deleteProcessId -> God.stopProcessId -> God.killProcess sends SIGINT (cst.KILL_SIGNAL, PM2_KILL_SIGNAL-overridable) to the process tree and polls up to pm2_env.kill_timeout (our ecosystem.config.cjs sets 10000ms) before escalating to SIGKILL (God/Methods.js's processIsDead). Our generated run.js launcher forwards SIGTERM/SIGINT/SIGHUP to the actual litellm child (stopChild()); litellm (uvicorn/FastAPI) does a standard graceful shutdown on SIGINT/SIGTERM — stop accepting new connections, let in-flight ones finish — before exiting. Only after that stop settles does pm2.start() bring up the newly-active connection. So AC#4 holds BY CONSTRUCTION — connections.activate adds no drain logic of its own and needed none; it just must not pre-empt this (it doesn't — no manual kill anywhere in the new handler). Windows caveat carried over unchanged from CLAUDE.md/configGen.js's own existing, pre-CCA-15 documentation: no real POSIX signals there, so this is a macOS/Linux guarantee; Windows already degrades to a harder stop, unrelated to and unchanged by this task.

Could NOT live-verify AC#4 end-to-end against a REAL pm2 daemon this session: investigated first (`pm2.list()` against the shared default PM2_HOME) and found a genuine litellm-nim app already running there — presumably this machine's real, in-use Claude Conduit proxy. pm2Control.startOrRestart()'s deleteAppIfPresent()+pm2.start() would have deleted and replaced that real running app (the pm2 app name is a global constant, NOT namespaced by NIM_PROXY_TEST_HOME — see CLAUDE.md's own note that the pm2 app name is deliberately untouched by the config-dir isolation), risking disruption to whatever real Claude Desktop/Code session is routing through it. Declined to run that test for safety. AC#4's verification is therefore the pm2-source-code trace above (an explicit, documented exception — CLAUDE.md's verification standard prefers live testing, but this is the "reading the library's own internals to establish its contract" case, and no in-repo test double could prove anything about the SIGINT/kill_timeout mechanics that doesn't already reduce to trusting pm2's own source), not a fresh live observation of a request surviving a real restart.

AC#5 (single-vs-multi-proxy, derived from THIS task's own AC#1/#2) — documented: AC#1 ("exactly one connection is active at a time") and AC#2 ("restarts the proxy", singular) already specify single-proxy as the model; connections.activate() literally only ever calls pm2Control.startOrRestart() once, against the one fixed `litellm-nim` pm2 app name — there is no code path anywhere in this change that starts a second pm2 app per connection. A multi-proxy design would need per-connection ports and per-connection pm2 app names, neither of which exist in the CCA-15.1 connection schema (port stays system-level, out of a connection, by CCA-15's own recorded decision) — so multi-proxy was never a live option once CCA-15.1 landed, not just a preference. Same reasoning already recorded on CCA-15's own Implementation Plan; restated here as this specific AC's evidence.

AC#6 (credentials stay in OS-backed secret storage through a switch, never written into the config directory) — verified: connections.activate reads the credential ONLY via secretStore.loadFor(id) (never .save/.saveFor — proven by a source-scan test) and manifest.json never contains a credential (verified live — see below). Documented nuance, carried over unchanged from this app's pre-CCA-15 architecture (DESIGN.md section 4 Step 4): the CURRENTLY-ACTIVE connection's key does flow into litellm.env, which lives inside the config directory — this is the same single, pre-existing, sanctioned runtime sink every config.generate/updatePort call has always written the active credential into (litellm itself, an external process, has no way to read the OS keychain directly), unchanged and un-widened by this task. Every connection NOT currently active, and the connections library's own persistent storage (manifest.json), never hold a credential at all — only secretStore does. Read AC#6 as extending that existing, accepted boundary to "many connections" (the actual CCA-15.1/15.2 work), not as a new requirement that litellm.env itself stop existing.

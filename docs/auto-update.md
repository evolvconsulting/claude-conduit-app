# Auto-update mechanism — how a shipped build learns a new version exists

Decided and implemented under **NCOW-10.1**, 2026-08-01. This is the record of *why* the
update story looks the way it does; `docs/distribution.md` (owned by a sibling task,
NCOW-10.2, and not edited here) covers the release/publish side — how a Release gets cut and
what it must contain. This document is the consuming side: what a running app does with that
Release once it exists.

---

## Decision — electron-updater against the GitHub Releases feed

**Mechanism:** [`electron-updater`](https://www.npmjs.com/package/electron-updater), reading
the `latest.yml` / `latest-mac.yml` / `latest-linux.yml` files electron-builder already emits
next to every published Release (confirmed working under NCOW-9 — see
`docs/distribution.md`'s "Packaging hardening" section). No second feed, no separate update
server, no build-config changes on top of what NCOW-9 already produces.

Why this over the alternatives:

- **It's the standard pairing.** electron-updater is built by the same project as
  electron-builder and consumes exactly the artifact layout `npm run dist` already produces.
  Anything else (a hand-rolled version-check-and-download, `update.electronjs.org`, a private
  update server) would mean maintaining a second publishing target for zero benefit — the
  GitHub Releases feed this app already uses for manual downloads is already correct.
- **The GitHub provider needs no explicit `publish:` config.** `docs/distribution.md`
  already established that electron-builder infers `repositoryInfo` from `package.json`'s
  `repository` field (not `.git`, which fails inside a worktree), and that this same
  inference is what produces `latest*.yml`. `app-update.yml` — the file electron-updater
  reads at runtime to know which repo to poll — is generated by the same inference, so
  nothing in `electron-builder.yml` needed to change for this task.

## Per-platform support matrix

| Platform | Mechanism | Silent install? | Notes |
|---|---|---|---|
| Windows (NSIS) | electron-updater, GitHub provider | **Yes** | No certificate required for electron-updater to download, verify (via its own hash check against `latest.yml`), and install an NSIS update. Real end-to-end verification against a published Release is NCOW-10.3, not this task. |
| Linux (AppImage) | electron-updater, GitHub provider | **Yes** | Same mechanism; electron-updater replaces the running AppImage in place. The `deb` target has no update mechanism at all — Debian/Ubuntu users on the `.deb` are expected to re-download, exactly like today. |
| macOS | GitHub Releases API check only (no electron-updater) | **No — notify-only** | See "Why macOS is notify-only" below. The app tells the user a newer version exists and links to the Release page; it never downloads or installs anything on macOS. |

## Why macOS is notify-only (final — do not re-litigate)

This supersedes an older, stale implementation note on the parent task (NCOW-10) that assumed
a fully signed macOS path. **That assumption was wrong for this campaign and the "ship
unsigned, macOS notify-only" decision below is final** — confirmed by the user, not up for
re-derivation here.

Squirrel.Mac (the framework electron-updater's `MacUpdater` drives on macOS) verifies a
downloaded update's code signature before installing it. `docs/distribution.md` already
verified, directly against a real build, that this app ships **ad-hoc signed, not notarized**
(`identity: "-"`, `spctl -a -t exec` rejects it) — there is no Developer ID certificate to
sign real update payloads with, and ad-hoc signatures are not what Squirrel.Mac accepts for
this. Handing an ad-hoc-signed build to electron-updater's Mac path would not silently
degrade — it would attempt a download and then fail at install, which is a worse experience
than never attempting it.

So on `darwin`, `src/main/autoUpdate.js` **never touches `electron-updater` at all**. Instead
it calls `src/engine/updateCheck.js`, which hits the GitHub Releases API
(`GET /repos/<owner>/<repo>/releases/latest`) directly and compares the tag against the
running version. If newer, the renderer shows a dismissible banner ("Update x.y.z available —
View release") that opens `https://github.com/evolvconsulting/claude-conduit/releases/latest`
via the already-allowlisted `app:open-external` channel. That's the entire macOS mechanism —
no download, no install, no Squirrel.Mac involvement whatsoever.

**Revisit trigger:** the moment a Developer ID certificate + notarization lands (tracked as a
follow-up in `docs/distribution.md`), macOS should be switched onto the same electron-updater
path Windows/Linux already use. Until then this is not a placeholder to "finish later
opportunistically" — it is the correct behavior for an unsigned build.

## In-app update checker

- **Automatic check:** fires on the very next microtask after `app.whenReady()`, from
  `src/main/index.js` — see `Promise.resolve().then(() => autoUpdate.checkForUpdates())`,
  deliberately never `await`ed so it cannot delay the window showing or anything else in
  startup (AC#4). Skipped entirely in unpackaged/`--dev` runs (`app.isPackaged` false) — there
  is no installed artifact for electron-updater to diff against, and no `app-update.yml` is
  even packed outside a real build.
- **Renderer re-sync:** that automatic check can — and on a fast macOS GitHub Releases check
  against a cold pm2 daemon, regularly does — broadcast its result before the renderer has even
  subscribed to `update:status-changed` (subscribing happens only after three awaited startup
  IPC calls, including `proxy.getStatus`, which can take 1s+ to connect to pm2 on its first
  launch). A push sent before anyone is listening is silently dropped. To recover from that,
  `src/renderer/app.js` calls `window.nimProxy.update.check()` again immediately after it
  subscribes. This is safe and cheap, not a second real check: `autoUpdate.js`'s
  `checkForUpdates()` caches the last broadcast status and coalesces overlapping calls, so a
  call landing after the first check already finished just replays the cached result, and a
  call landing while one is still in flight joins it — neither case re-hits GitHub or
  electron-updater. (Re-hitting electron-updater's `checkForUpdates()` concurrently is not just
  wasteful — it can start a second download against the same pending-update cache directory
  mid-download and corrupt whichever one loses the race.)
- **Manual re-check / renderer surface:** `window.nimProxy.update.check()` (IPC channel
  `update:check`) is the same entry point described above — it re-runs the check only if none
  has completed yet or one is already in flight; otherwise it replays the last known status.
  Status is pushed to the renderer over `update:status-changed`
  (`window.nimProxy.update.onStatusChanged(...)`) — the renderer's CSP sets `connect-src
  'none'`, so it could never poll GitHub itself; every network call this feature makes happens
  in the main/engine layer only, exactly like `licenses.json`.
- **UI:** `src/renderer/components/update-banner.js` — a small, dismissible, non-auto-expiring
  banner (not a `window.confirm/alert`, which freezes the whole renderer — see CLAUDE.md).
  Only two states render anything: `downloaded` (Windows/Linux — "Restart to install") and
  `notify-only` (macOS — "View release"). `checking` / `not-available` / `skipped` / `error`
  render nothing in the UI; failures are still logged in the main process (see
  `src/main/autoUpdate.js`) so they're diagnosable without being intrusive.

## Graceful degradation (AC#4)

Every failure mode — offline, DNS failure, GitHub rate-limiting (403/429), a 5xx, a malformed
response, no Release published yet (404, genuinely true pre-1.0), or electron-updater's own
`error` event / a rejecting `checkForUpdates()` call — resolves to a status object
(`{state: 'error', message}` or `{state: 'not-available', ...}` for the "no release yet"
case), never a thrown/rejected promise out of `checkForUpdates()`. See
`src/engine/updateCheck.js` (the GitHub API check, used directly on macOS) and
`src/main/autoUpdate.js` (the Windows/Linux electron-updater wrapper) — both are unit tested
against every one of these failure modes, including a hung network call bounded by a
non-negotiable timeout so a wedged check can never hang anything.

The check is never `await`ed on the startup path (see above), so even a failure mode that
somehow *did* throw synchronously would only ever trip the `.catch()` backstop in
`index.js`, not block `createMainWindow()`.

## Proxy behaviour across an app update/restart (AC#5)

An update install is, at the process level, exactly a quit followed by a relaunch into the
new binary — so it goes through the same proxy-stop mechanism as a normal quit
(`shutdown.js`'s `createProxyShutdown`, the same one `main/index.js`'s `before-quit` handler
already uses), not a second, invented one.

**Design:**

- Installing is never automatic on a plain quit. `autoUpdater.autoInstallOnAppQuit` is set to
  `false` explicitly. The alternative — letting a downloaded update silently install itself
  the next time the user quits normally — was rejected because electron-updater adds its own
  internal `before-quit` listener once a download completes (`BaseUpdater.addQuitHandler()`),
  and that listener's timing relative to this app's own asynchronous proxy-stop (which
  `preventDefault()`s the first `before-quit` pass, stops litellm-nim, then re-issues
  `app.quit()`) is not something this app controls or can verify deterministically without
  reading electron-updater's internals build-by-build. Requiring an explicit action removes
  that race entirely.
- The explicit action is `window.nimProxy.update.install()` (IPC channel `update:install`),
  which calls `src/main/autoUpdate.js`'s `installUpdateAndRestart()`:
  1. Stops the status poller (so no stale "running" tick repaints mid-shutdown — mirrors
     `before-quit`'s own ordering).
  2. `await`s the exact same `stopProxyForShutdown()` function `before-quit` calls — stopping
     only the `litellm-nim` pm2 app, never the shared pm2 daemon (see `shutdown.js`).
  3. Sets the same `shuttingDown` latch `before-quit` checks, so if `autoUpdater.
     quitAndInstall()` triggers Electron's own `before-quit` internally, that handler's
     stop-then-requit dance steps aside instead of trying to stop an already-stopped proxy a
     second time.
  4. Calls `autoUpdater.quitAndInstall()`.
- Guarded against double-invocation (`installInProgress`) so two fast clicks, or a click
  racing the automatic check, can't stop the proxy or install twice.
- On macOS, this code path is unreachable in practice — `update-downloaded` never fires
  because electron-updater is never invoked there at all (see above).

Unit tested in `test/main/autoUpdate.test.js`, including the exact call ordering
(`stopStatusPoller` → `stopProxyForShutdown` → `markShuttingDown` → `quitAndInstall`) and the
double-invocation guard.

## What this task does not cover

- **Real end-to-end verification** — installing an old build and watching it actually fetch,
  download, and apply an update against a live published GitHub Release — is a separate
  follow-on task, **NCOW-10.3**. Nothing here has been exercised against a real Release feed;
  every test uses injected fakes (see `test/engine/updateCheck.test.js` and
  `test/main/autoUpdate.test.js`).
- **`docs/distribution.md`** — release-cutting, asset naming, `SHA256SUMS`, the CI release
  workflow — is owned by NCOW-10.2 and intentionally untouched here.
- **macOS code signing/notarization** and the eventual switch of macOS onto the same
  electron-updater path Windows/Linux use — tracked as a revisit trigger in
  `docs/distribution.md`, not in scope for this task.
